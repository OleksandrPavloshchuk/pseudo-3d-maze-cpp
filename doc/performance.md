О, ось тепер починається найцікавіше! 🙂 Ти фактично перейшов від експерименту з `std::thread` до невеликого дослідження продуктивності.

Я б запропонував зробити окремий вимірювач, який збиратиме статистику за серією кадрів. І обов'язково рахувати не лише середнє арифметичне, а й медіану та перцентилі.

Чому 1600×1200 на 16 потоках могло лягти? Є кілька можливостей:

- надмірна кількість потоків і витрати на їх створення;
- конкуренція за кеші та пропускну здатність пам'яті;
- помилка в індексації або записах у framebuffer;
- проблема в SDL, якщо паралельно викликаються функції SDL.

Останній пункт особливо важливий: у робочих потоках я б залишив тільки запис у власний framebuffer, а всі операції SDL — у головному потоці.

## **1. Чим вимірювати**

У C++ є чудовий стандартний інструмент — `std::chrono::steady_clock`.

Він призначений саме для вимірювання проміжків часу: на відміну від системного календарного часу, він монотонний.

Наприклад:

```
using Clock = std::chrono::steady_clock;

const auto start = Clock::now();

updateFrameBuffer();

const auto finish = Clock::now();

const auto elapsed =
    std::chrono::duration<double, std::milli>(finish - start).count();
```

Отримаєш час у мілісекундах із дробовою частиною.

## **2. Збір статистики**

Для початку я б зробив максимально простий клас:

```
struct RenderStats {
    std::vector<double> samples;

    void add(double milliseconds) {
        samples.push_back(milliseconds);
    }

    double mean() const {
        double sum = 0;

        for (double value : samples) {
            sum += value;
        }

        return sum / samples.size();
    }

    double percentile(double p) const {
        auto sorted = samples;
        std::sort(sorted.begin(), sorted.end());

        const size_t index = static_cast<size_t>(
            std::ceil(p * sorted.size())
        ) - 1;

        return sorted[index];
    }

    double median() const {
        auto sorted = samples;
        std::sort(sorted.begin(), sorted.end());

        const size_t middle = sorted.size() / 2;

        if (sorted.size() % 2 == 0) {
            return (sorted[middle - 1] + sorted[middle]) / 2.0;
        }

        return sorted[middle];
    }
};
```

Тут потрібні:

```
#include <algorithm>
#include <cmath>
#include <vector>
```

Для повноти я б ще додав мінімум і максимум, але вже цього достатньо для першого дослідження.

## **3. Як організувати експеримент**

Я б не вимірював кожен кадр нескінченно. Зробив би окремий тестовий режим:

```
RenderStats stats;

constexpr int warmupFrames = 30;
constexpr int measuredFrames = 500;

for (int i = 0; i < warmupFrames; ++i) {
    updateFrameBuffer();
}

for (int i = 0; i < measuredFrames; ++i) {
    const auto start = Clock::now();

    updateFrameBuffer();

    const auto finish = Clock::now();

    const double elapsed =
        std::chrono::duration<double, std::milli>(
            finish - start
        ).count();

    stats.add(elapsed);
}
```

Перші 30 кадрів відкидаємо: нехай прогріються кеші, код і все інше.

500 наступних кадрів записуємо.

Важливо: не роби `std::cout` усередині циклу вимірювання. Виводь результати лише після завершення.

## **4. Які показники дивитися**

Я б виводив приблизно таку таблицю:

| Показник | Що означає                       |
| -------- | -------------------------------- |
| Min      | Найшвидший кадр                  |
| Mean     | Середній час                     |
| Median   | Типовий час                      |
| P95      | 95% кадрів швидші за це значення |
| P99      | 99% кадрів швидші за це значення |
| Max      | Найповільніший кадр              |

Особливо цікавий P95. Він показує, наскільки стабільний рендеринг, а не лише наскільки швидким він буває за сприятливих обставин.

Медіана теж корисна: вона менш чутлива до випадкових затримок операційної системи.

## **5. Що ще я б дослідив**

Мені здається, найцікавіший результат буде не просто порівняння 1, 2, 4, 8, 16 потоків, а побудова залежності часу рендерингу від кількості потоків.

Наприклад, умовна таблиця:

| Потоки | Час, ms | Прискорення |
| ------ | ------- | ----------- |
| 1      | 40      | 1.00x       |
| 2      | 23      | 1.74x       |
| 4      | 14      | 2.86x       |
| 8      | 12      | 3.33x       |
| 16     | 15      | 2.67x       |

Цифри умовні, лише для ілюстрації.

Тут добре видно, що після певної кількості потоків додатковий паралелізм уже не допомагає, а навіть шкодить.

Я б також окремо перевірив дві речі:

- Вимірювання з урахуванням створення та знищення потоків (твоя поточна реалізація).
- Вимірювання з постійно працюючими потоками, які отримують нові завдання.

Це дозволить побачити, скільки коштує саме організація багатопотоковості.

**І щодо падіння на 1600×1200:** я б поки не списував його на нестачу ресурсів. Якщо це саме аварійне завершення, а не зависання, варто подивитися stack trace всіх потоків у GDB (`thread apply all bt`). Особливо цікаво, що відбувається всередині `drawVerticalLine()`.

І ще одна думка: коли отримаєш результати, можна буде побудувати графік залежності часу від кількості потоків для кількох розмірів framebuffer. Це вже буде цілком пристойний маленький benchmark.

Мені подобається цей експеримент ще й тим, що він не вимагає вигадувати штучне навантаження: у тебе є справжній алгоритм із реальною роботою, який можна оптимізувати й вимірювати.
